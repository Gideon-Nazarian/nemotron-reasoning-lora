## What v5 tested

**Hypothesis:** filling the `transformation_rules` hole (0% solver coverage, 16% of the test set with no training signal) lifts LB without perturbing covered categories. Specifically, the bet was that "fill a hole" data is fundamentally different from "perturb a covered category" data (which is what v4 did and how it regressed by −0.02).

**Data construction:** 800 hand-crafted synthetic transformation_rules examples generated by `scripts/synth_transformation_rules.py`:
- 400 numeric problems (obfuscated arithmetic operators: add, subtract, multiply, div_floor, mod, concat, swap-concat, digit_sum, digit_diff, max, min, avg, xor_digit)
- 400 symbolic problems (5-char punctuation strings under positional/structural rules: reverse, first_N, last_N, drop_at, keep_positions, swap, double_first, every_other, take_unique)
- Reasoning template: "hypothesize rule X, verify against examples (reject if mismatched), hypothesize rule Y, confirm against all examples, apply to question"

**Critically: the 4681 solver-generated records are byte-identical to v3.** No covered category got new data; no existing data got modified.

Two consecutive data-modification experiments, both costing exactly −0.02. This is statistically unlikely to be coincidence on 5000-problem test sets.

## Revised diagnosis

My earlier theory (v9 diagnostic notes): "more-and-still-correct training data is NOT a monotonic lever" — confirmed and strengthened by v5.

But the new wrinkle: v5 was supposed to AVOID the v4 failure mode by filling an uncovered hole rather than perturbing a covered category. It regressed by the SAME amount anyway. So the failure mode is broader than "perturbing covered categories":

**v3 represents a local optimum for the data shape we used.** Adding ANY data — whether to covered categories or uncovered ones — appears to shift the model's calibration in a way that costs ~0.02 LB.

**Plausible underlying mechanism:** the 800 synthetic transformation_rules records used "hypothesis-test-apply" reasoning ("Try addition: doesn't fit. Try subtraction: ✓") — a structurally different pattern from v3's Fix A reasoning ("Apply formula F: F(a,b) = result"). The model probably tried to over-generalize the new pattern onto other categories where it doesn't apply, costing more LB points than the transformation_rules problems gained.

This is a **subtle but important lesson**: it's not enough for new training data to be "correct" — it has to MATCH the reasoning shape the model has already learned for other categories. Otherwise the new pattern leaks into categories that already work.
